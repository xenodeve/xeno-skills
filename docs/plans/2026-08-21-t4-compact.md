# T4-Compact — compaction at a semantic boundary, not at the ceiling

**Status:** design, not started. **PRD: #304**; slices #305 (probe) · #306 (validity) · #307 (gate) · #308 (skill) · #309 (restore), attached as native sub-issues. Tracking issue #310.
**Source of the concept:** `C:\AI\docs\researchs\Qwen3.8-27B_Optimization_Research_Docs\07-CONTEXT-KV-CACHE-T4-COMPACT.md` §9 (2026-08-17), restated by the developer on 2026-08-21 as a *software layer the model calls*.

> **Revision 2, 2026-08-21.** Revision 1 of this file said the layer should stop trying to trigger
> compaction and instead make the harness's own compaction safe. **The developer rejected it, correctly:**
> auto-compaction fires only when the window is effectively full, so riding it covers **one** of the four
> conditions — the emergency one — and none of the three that make the idea worth building. Revision 1
> answered *"make compaction safe"*; the goal is *"compact at the right moment"*. What follows is the
> corrected design, and §2 is why the goal is reachable after all.

---

## 1. The requirement, in the developer's terms

A **software layer around the session that the model can call**. The skill decides a boundary has been
reached; the layer does `/handoff`, then compaction, then hands the model a prompt pointing at the
handoff by path. Four conditions must reach it, **all of them before the window is full**:

1. context is long
2. a task finished and the next has not started
3. the context is large enough that error and hallucination risk are rising
4. what is left does not fit the task about to start

**Conditions 2–4 are the product.** Condition 1 alone is what the harness already does badly.

## 2. The trigger surface, measured (2026-08-21, `grep -a` on the shipped binary and the SDK types)

| Finding | Evidence | What it means here |
|---|---|---|
| **The model has no compaction tool** | `sdk-tools.d.ts` enumerates every tool input type: `Bash`, `FileEdit`, `Task*`, `AskUserQuestion`, `Workflow`… — **no `SlashCommand`, no compact** | The model cannot press the button. This part of revision 1 stands. |
| **Auto-compaction is threshold-driven, and the threshold is configurable** | a `/autocompact` command — `description: "Configure the auto-compact window size"`, `argumentHint: "[auto|<tokens>]"`, `supportsNonInteractive: !0` — plus **`CLAUDE_CODE_AUTO_COMPACT_WINDOW`** and `resolveAutoCompactWindow` *"clamped to the model window, honoring /autocompact, CLAUDE_CODE_AUTO_COMPACT_WINDOW, clientdata and experiment"* | **"only at 100%" is the default, not a law.** A smaller window is a compaction that happens sooner. |
| **A second, cheaper compaction already runs** | `tengu_time_based_microcompact` with `toolsCleared` / `toolsKept` / `keepRecent` / `tokensSaved` and `trigger: context_hint`; `compact_micro_keep_recent`; a distinct **`microcompact_boundary`** record | Old **tool results** are flushed periodically, keeping recent ones. No summary, no handoff — a different instrument for a different job. |
| **`PreCompact` can block** | `Compaction blocked by PreCompact hook` · `compaction blocked by PreCompact hook; continuing uncompacted` | The invariant `NO VALID HANDOFF → NO COMPACT` is enforceable. |
| **`PostCompact` exists, and hooks can add context** | `executePostCompactHooks`, `additionalContext` | The restore step needs no new event. |
| Compaction can be turned off entirely | `autoCompactEnabled`, `DISABLE_AUTO_COMPACT`, and `DISABLE_COMPACT` — *"also disables manual /compact"* | The layer must not assume compaction is available; it can be off. |

**So there are three levers, not one**, and the layer's job is to pick between them:

```text
microcompact   flush old tool results        cheap, already automatic, no handoff needed
window         move the auto-compact ceiling  a compaction that happens EARLIER, no keystroke
/compact       full summarise + restart       needs a keystroke nobody in-session can produce
```

## 3. The design: the layer moves the ceiling, it does not press the button

**The model signals; the layer sets the window; the harness compacts.** Nothing has to type anything.

```text
skill detects a boundary
  → /handoff, to a session-keyed path
  → validate the handoff (else stop here — an unusable handoff is not a boundary)
  → ask the layer for a window that is BELOW current usage
  → the harness's own auto-compaction fires, at the moment we chose
  → PostCompact / SessionStart injects: read the handoff at <path>
  → continue
```

**Whether the window can be lowered mid-session by anything other than a person typing `/autocompact`
is the one unknown this design rests on, and it is slice #305.** Three candidates, in the order the
probe should try them:

1. **`CLAUDE_CODE_AUTO_COMPACT_WINDOW`** — if `resolveAutoCompactWindow` reads it per turn rather than at
   boot, a hook can export it and the next check picks it up. Cheapest by far.
2. **A hook-visible setting** — `.claude/settings.json` or `clientdata`, if either is re-read live.
3. **A supervisor that owns the session's stdin** — the wrapper the developer described, typing
   `/autocompact <n>` or `/compact`. Real, and the most expensive: on Windows the TUI needs a console,
   so this is console automation, not a pipe.

**If all three fail**, the honest fallback is condition 2 with a human in the loop: the skill writes the
handoff and says *"`/compact` when you're ready"* — one keystroke, at a moment that is now correct
instead of accidental. That fallback is worth shipping on its own, and it is the same skill.

## 4. Which lever each condition pulls

| Condition | Lever | Why |
|---|---|---|
| **2. task finished, next not started** | **window** — lower it now, at the clean boundary | This is the whole point: the summary is written where the work has a natural seam, not mid-thought. |
| **4. what is left does not fit the next task** | **window**, sized from the task | The change-site survey already estimates the next task's size; this is that number, spent. |
| **1. context is long** | **microcompact first**, window if it keeps growing | Tool results are usually most of it, and flushing them costs no summary and no restart. |
| **3. error risk rises with depth** | **unproven — no lever yet** | The adjacent project's depth data **does not support it**: `03-DEEP-CONTEXT-QUALITY-REPORT.md` reads **100 % (30/30) at 64K** and **100 % (10/10) at a 114,406-token prompt** — verified by reading that file, lines 94 and 160. One quantization, and *no degradation detected* is not *equivalence shown*. Ships as a stated hypothesis, never as a trigger. |

**Conditions 1 and 2 ship as triggers. Conditions 3 and 4 do not ship as triggers**: 3 is unmeasured
here, and 4 needs a size estimate the skill cannot produce alone.

## 5. The guard, unchanged from revision 1 — and it is still the part that pays

The invariant holds whichever lever fires, **including a compaction we did not ask for**:

| trigger | handoff valid | behaviour |
|---|---|---|
| `manual` | yes | allow |
| `manual` | no | **block**, naming the path it looked at |
| `auto` | yes | allow |
| `auto` | no | **allow**, warn, and **record the event** |

**Blocking an automatic compaction is still not the safe half.** It fires because the window is full —
now possibly a window *we* lowered — so refusing it wedges the session. The recorded rate of
`auto`-without-handoff is the measurement that tells us whether the skill's conditions fire early enough.

**And a valid handoff is a precondition of lowering the window, not a consequence.** The layer never
moves the ceiling before the handoff validates; otherwise it has scheduled a compaction it cannot survive.

## 6. Slices

1. **#305 — probe the trigger surface.** Can the auto-compact window be lowered mid-session by a hook
   (env, setting, clientdata)? Does a lowered window compact immediately or at the next check? What does
   `PreCompact` receive, and how is a block expressed? **No shipped behaviour** — every other slice
   depends on which of §3's three candidates works, and one of them decides whether this is a hook or a
   supervisor process.
2. **#306 — handoff path convention + validity.** Session-keyed, non-empty, required sections, **newer
   than the last compaction boundary**. A stale handoff satisfies the invariant falsely.
3. **#307 — the `PreCompact` gate**, implementing §5.
4. **#308 — the skill `t4-compact`.** Conditions 1–2 as triggers, 3–4 as stated hypotheses; writes the
   handoff; asks the layer for a window; and if no lever exists, says the one line to the developer.
5. **#309 — restore names a path**, asserted against the hook's real output.

Slices 2–5 each carry a `tests/` suite; slice 1 carries a fixture and a finding.

**An addon extends slices 2, 4 and 5 without adding a stage:**
[`2026-08-21-t4-compact-addon-thinking-record.md`](2026-08-21-t4-compact-addon-thinking-record.md) keeps
the **reasoning** that produced each conclusion, mapped by an index the restore step names beside the
handoff. Its load-bearing clause lands in slice 2's validator: **an orphaned record — a file missing from
the index, or an index entry with no file — invalidates the handoff**, so §5's table is the enforcement
point and no new event is introduced. Read it after this file; it does not re-plan anything here.

## 7. What this plan deliberately does not do

- **It does not re-plan #182 or #184** — injection cost and boundary-aware presence counting are done.
- **It does not build the source document's nine-state machine.** With the window as the lever, six of
  those states are the harness's own; ours are *boundary detected*, *handoff valid*, *window set*.
- **It does not touch the delegation layer** — `BrainstormRequest v1` governs a different prompt.
- **It does not assume compaction is available.** `DISABLE_COMPACT` turns off even the manual path, and
  the skill must degrade to *write the handoff and say so* rather than fail.
